# Scheduled Task Claiming — Design

**Status:** implemented
**Date:** 2026-08-07

## Problem

The scheduler polls once per minute, but it advances a task's `next_run` only
after the task container finishes. Any run lasting longer than one poll remains
visible to `getDueTasks()` throughout its execution.

`GroupQueue.enqueueTask()` deduplicates only entries already in
`pendingTasks`. It does not record the ID of the task currently executing. The
next scheduler poll therefore queues the same task again, and `drainGroup()`
runs that duplicate immediately after the original completes.

This is observable on staging:

- `soul-evening-journal-main` produced 26 duplicate follow-up runs in the last
  30 days.
- The duplicates have the same task ID and group, and begin roughly one
  scheduler interval after the original.
- Other long-running scheduled tasks exhibit the same pattern.

This is a scheduler ownership bug, not multi-soul fan-out. Spawned souls do not
own separate copies of these scheduled tasks.

## Goal

Atomically claim each due schedule occurrence before it enters `GroupQueue`, so
one occurrence can be queued or running at most once across scheduler polls.
Define deterministic release and restart recovery without changing user-facing
task statuses or schedule semantics.

## Non-goals

- Exactly-once external side effects. A host crash after an agent sends a
  message but before completion is recorded can still require operator judgment.
- Running different tasks for the same group concurrently. Existing per-group
  serialization remains unchanged.
- Changing cron, interval, or one-shot next-run calculations.
- Giving spawned souls independent schedules.
- Removing historical duplicate `task_run_logs` rows or duplicate messages.
- General distributed scheduling. NanoClaw remains a single-host application,
  though atomic claims protect against overlapping scheduler loops/processes.

## Design

### 1. Add claim metadata to `scheduled_tasks`

Add two nullable columns in `createSchema()` using the existing idempotent core
schema-migration pattern:

```sql
ALTER TABLE scheduled_tasks ADD COLUMN claim_token TEXT;
ALTER TABLE scheduled_tasks ADD COLUMN claimed_at TEXT;
```

Add an index supporting due-task discovery:

```sql
CREATE INDEX IF NOT EXISTS idx_scheduled_tasks_claim
  ON scheduled_tasks(status, next_run, claim_token);
```

`claim_token` is an opaque UUID generated by the scheduler for one occurrence.
`claimed_at` is operational evidence and supports recovery diagnostics. Neither
field changes the public `status` values (`active`, `paused`, `completed`).

Extend `ScheduledTask` with optional nullable `claim_token` and `claimed_at`
fields so rows remain compatible during migration and in tests.

### 2. Replace read-then-enqueue with atomic claiming

Replace `getDueTasks()` in the scheduler path with:

```ts
export interface ClaimedTask extends ScheduledTask {
  claim_token: string;
  claimed_at: string;
}

export function claimDueTasks(
  now: Date = new Date(),
  limit = MAX_CONCURRENT_CONTAINERS,
): ClaimedTask[];
```

`claimDueTasks` runs in one `better-sqlite3` immediate transaction:

1. Select tasks where `status = 'active'`, `next_run <= now`, and
   `claim_token IS NULL`, ordered by `next_run`, limited to `limit`.
2. For each row, generate a UUID and conditionally update it:

   ```sql
   UPDATE scheduled_tasks
      SET claim_token = ?, claimed_at = ?
    WHERE id = ?
      AND status = 'active'
      AND next_run IS NOT NULL
      AND next_run <= ?
      AND claim_token IS NULL
   ```

3. Return only rows whose conditional update changed one row, including their
   token.

The transaction makes discovery and ownership indivisible. Every later poll
excludes the claimed occurrence whether it is waiting in `GroupQueue` or
already running.

The limit bounds how many claimed tasks can sit in memory, but correctness must
not depend on it. A claimed task may remain queued longer than a container run.

### 3. Carry the claim through execution

`startSchedulerLoop()` enqueues each `ClaimedTask`; `runTask()` retains its
claim token through capability gating, validation, container execution, and
error handling.

Remove the current post-query `getTaskById()` recheck. The conditional claim is
the authoritative active/due check and closes the race between reading a due
row and enqueueing it.

Every terminal path must finalize or release the exact claim token:

- capability hook skips the run;
- group is missing;
- container succeeds;
- container reports an error;
- setup or execution throws before a container starts.

All finalization updates use both task ID and token in the `WHERE` clause. A
stale worker must never overwrite a newer occurrence.

### 4. Finalize occurrence and release claim atomically

Replace `updateTaskAfterRun()` in scheduled execution with a token-aware
operation:

```ts
export function finalizeClaimedTask(
  id: string,
  claimToken: string,
  nextRun: string | null,
  lastResult: string,
): boolean;
```

It performs:

```sql
UPDATE scheduled_tasks
   SET next_run = ?,
       last_run = ?,
       last_result = ?,
       status = CASE WHEN ? IS NULL THEN 'completed' ELSE status END,
       claim_token = NULL,
       claimed_at = NULL
 WHERE id = ? AND claim_token = ?
```

The return value is `true` only when one row was updated. A false result is
logged as a claim-ownership error.

Task-run logging and task finalization should execute in a single transaction
after execution. This prevents a normal process error from recording a run but
leaving the same occurrence claimed, or advancing the schedule without its run
record.

For a capability-gated run, advance `next_run` and clear the claim as today,
without inserting a `task_run_logs` row. For a missing group, retain today's
error log entry and advance the schedule, but finalize with the claim token.

Keep the existing unrestricted `updateTaskAfterRun()` only if non-scheduler
callers require it; otherwise remove it to prevent bypassing claim ownership.

### 5. Recover claims after interruption

On process startup, after `initDatabase()` and before starting the scheduler,
call:

```ts
export function releaseInterruptedTaskClaims(): number;
```

For this single-host architecture, every claim present before the new host
process starts belongs to an interrupted prior process. Clear `claim_token` and
`claimed_at` while leaving `next_run` unchanged. The occurrence becomes due
again and is retried normally. Log the number and IDs of released claims.

This gives at-least-once crash recovery. It intentionally prefers retrying an
interrupted occurrence over silently losing it. The system cannot guarantee
exactly-once outbound messages across a crash because channel sends are not
transactional with SQLite.

Do not expire live claims by age. Containers may legitimately run for the full
configured timeout, and tasks may wait behind other work. Age-based expiry
would recreate the same duplication bug for sufficiently long runs.

If multiple NanoClaw host processes are supported later, add a process lease
and heartbeat before changing this recovery rule. They are not part of the
current architecture.

### 6. Keep queue-level defensive deduplication

Add `activeTaskId: string | null` to `GroupState` as a secondary invariant:

- Set it before invoking a task function in `runTask()`.
- Clear it in `finally` before draining the group.
- In `enqueueTask()`, return early when `activeTaskId === taskId` or the ID is
  already in `pendingTasks`.

The database claim is the correctness boundary. Queue deduplication is defense
in depth and protects direct/test callers that do not originate from the
scheduler.

## State transitions

```text
active + due + unclaimed
        |
        | atomic claim
        v
active + due + claimed ----> queued ----> running
        |                                  |
        | startup recovery                 | finalize by matching token
        v                                  v
active + due + unclaimed          active + next occurrence + unclaimed
                                  or completed + unclaimed (once task)
```

Pausing or cancelling a claimed task affects future scheduling but does not
force-kill a container already running. Finalization must preserve an explicit
`paused` status rather than changing it back to `active`. Deleting a task keeps
the existing queue caveat: an already captured task function may finish, but
its token-aware finalization updates zero rows and logs lost ownership.

## Schedule semantics

- Cron: calculate the next occurrence using the existing timezone-aware parser
  after the run or gated skip.
- Interval: preserve current fixed-delay behavior (`completion time + interval`).
- Once: finalize with `next_run = null` and `status = completed`.
- Claims represent one current occurrence; they do not create catch-up runs for
  every missed cron boundary.

## Testing

### Database tests (`src/db.test.ts`)

- `claimDueTasks` claims an active due task and excludes it from a second claim.
- A future, paused, completed, or already-claimed task is not returned.
- Two due tasks receive distinct non-null tokens.
- `finalizeClaimedTask` advances and releases only with the matching token.
- A wrong or stale token cannot alter the row.
- A once task becomes completed and unclaimed.
- `releaseInterruptedTaskClaims` releases claims without changing `next_run`,
  status, or task content.
- Claim selection respects due-time ordering and limit.

### Queue tests (`src/group-queue.test.ts`)

- Enqueueing the currently running task ID is ignored.
- Enqueueing the same pending task ID remains ignored.
- A different task for the same group queues and runs afterward.
- `activeTaskId` is cleared after success and failure, allowing the task's next
  occurrence to run later.

### Scheduler tests (new `src/task-scheduler.test.ts`)

- With a task blocked for more than two poll intervals, exactly one queue entry
  and one execution occur.
- A claimed task queued behind group work is not claimed again.
- Success, error, thrown setup, missing-group, and capability-gated paths all
  release their claims and advance correctly.
- A startup-interrupted claim is released and retried.
- A stale completion token cannot finalize a newly claimed occurrence.

Use fake timers and injected `now`/poll dependencies rather than waiting for
real one-minute intervals. The scheduler's module-level `schedulerRunning`
flag should be resettable in tests or the polling body should be extracted into
a testable `pollSchedulerOnce()` function.

### Regression acceptance test

Model a 90-second task with a 60-second scheduler poll. Before the fix it runs
twice; after the fix:

- one task container starts;
- one `task_run_logs` row is inserted;
- one outbound result is eligible to send;
- `next_run` advances once;
- claim fields are null after completion.

## Observability and deployment verification

Add structured logs for:

- `Scheduled task claimed`: task ID, claim token prefix, claimed time;
- `Interrupted task claims released`: count and task IDs;
- `Task claim ownership lost`: task ID and token prefix.

After deployment:

1. Confirm the migration added both columns and no pre-existing task is left
   claimed.
2. Confirm the service has one host process and starts without migration errors.
3. Observe at least one task lasting beyond 60 seconds.
4. Verify no second `Running scheduled task` event appears for its task ID
   before completion.
5. Verify exactly one run-log row and one schedule advance for that occurrence.
6. Query for sub-three-minute same-task run pairs after deployment; expect zero.

## Rollout and compatibility

This is an additive SQLite migration and needs no data backfill. Existing rows
default to unclaimed. The deployed `dist/` must be built from the same commit as
the source migration before restart.

Rollback to older code leaves the nullable columns unused and is schema-safe,
but older code does not honor claims. Before rollback, stop the service and
clear any non-null claims so the old scheduler does not inherit an ambiguous
in-flight occurrence.

## Alternatives rejected

- **Only track `activeTaskId` in `GroupQueue`:** fixes the observed single-
  process race but has no durable ownership or restart semantics.
- **Advance `next_run` before execution:** simple, but a crash can silently lose
  the occurrence and obscures whether it ran.
- **Set public status to `running`:** leaks execution state into user-facing
  task management and complicates pause/resume behavior.
- **Expire claims after the container timeout:** unsafe for tasks waiting in the
  queue and custom longer timeouts; can create duplicates again.
- **Insert the run log as the claim:** overloads completion history with
  unfinished rows and still needs ownership/recovery metadata.
